# Stair-Edge / Drop-Off Response: Recovery for Ledge Events

**Module:** recovery-safety · **Author:** OsakaTX · **Status:** design proposal
(reference logic shipping, awaiting review — NO auto-PR)

This document designs the *response* layer for ledge / drop-off events — the
behaviour that happens **after** the immediate safety stop at a stair edge,
ledge, or threshold. It deliberately **complements** the merged xbattlax
recovery work and this module's [DESIGN.md](./DESIGN.md) §5 safety hierarchy;
it does not duplicate either. The reference implementation is
[`roe/drop_off_response.py`](./roe/drop_off_response.py) (pure Python,
headless-testable) with 32 tests — see §7.

---

## 1. Why this is needed (verified gap, not speculation)

OOMWOO has real anti-fall (cliff) hardware: the merged part-specs document
**4× anti-fall IR cliff sensors** read via STM32/reference ADC with
explicit per-side bits in the sensor packet (`gd32-sensor-packet-and-connectors.md`: packet `0x03` Cliff flags; `0x78/0x79` Cliff IR control/direction;
io-board-sensors-and-motors-schematic.md §7 *"Anti-Fall (Cliff) IR Sensors"*).
A robot with cliff sensors and a cleaning mission WILL encounter edges, so the
motion stack needs a defined response.

Today the merged recovery logic only *stops* at a ledge:

- xbattlax's `oomwoo_recovery_safety` core.py treats `CLIFF`, `WHEEL_DROP`,
  `PICKUP`, `E_STOP` as **`SAFETY_SITUATIONS`** and routes every one through
  `_pause(...)`: `STATUS_ONLY`, `recoverable=False`, **no ladder**. The only
  way back to `IDLE` is an explicit `/oomwoo/recovery/reset`, and even that
  just clears the pause — it does not move the robot off the edge.
- The node (`recovery_node.py`) subscribes `/oomwoo/safety/cliff`,
  `/oomwoo/safety/wheel_drop`, `/oomwoo/safety/pickup` as Bool topics and
  calls the same pause on `True`.
- DESIGN.md §5 (this module) documents the same pause-only row for cliff and
  wheel-drop (priority 2 and 3, "Immediate stop … Manual clear + reset").

**Consequence:** a robot that drives up to a stair edge parks there, stops, and
stays paused until a human resets it. That is correct safety but incomplete
recovery. This document adds a bounded, guaranteed-terminating **escape
manoeuvre** for the ledge case and an explicit **pause-and-alert** escalation
for the case where autonomous escape cannot succeed.

Real-world relevance is anchored by upstream **issue #52 ("Stair climbing",
open 2026-08-05)**: the request references driving onto an external harness at
a stair. Whether or not that harness ships, every interaction with a stair /
ledge / step-down on the floor plan passes through this ledge-response path,
and a drop-off response is a prerequisite for any future stair-climbing
feature. This design intentionally does **not** try to climb stairs; it gets
the robot safely away from, and back to work at, an edge.

## 3. Design principles

1. **Safety first, always.** The response never removes the immediate stop.
   The first action on any ledge event is `stop=True` (matches DESIGN §5
   arbitration rule 1 and xbattlax's pause). This layer adds what happens
   after, preempted by nothing below priority 2.
2. **Priority: safety > operator > recovery.** A ledge event preempts bumper
   recovery AND operator teleop override (a human driver must not drive over
   a cliff either). This mirrors the `OperatorOverrideArbiter` contract and
   DESIGN §5 arbitration rule 4.
3. **Don't react to noise.** IR cliff reflectance is notoriously threshold
   sensitive: carpet shadows, dark rugs under glossy light, and sensor
   noise produce transient "cliff" blips at floor level. A persistence
   (debounce) window distinguishes a real edge from a blip before any motion
   is commanded.
4. **Every phase terminates.** Each phase carries a watchdog deadline; if a
   manoeuvre cannot complete (e.g. odometry frozen), the machine escalates to
   `PAUSED_AT_EDGE` + alert rather than looping forever.
5. **Distinguish a ledge from a wheelie.** A wheel-drop while the robot is
   still making commanded forward progress is a **transient traction event**
   (driving over an uneven threshold / small object), not a ledge, and must
   not trigger a full back-off. See §5.3.
6. **Prefer measured motion over open-loop time.** Back-off distance is
   measured from integrated odometry (module receives displacement; it does
   not read topics — same pattern as DESIGN.md open question #2). Re-orient
   completion is *acknowledged by the node* (verified heading), with a
   duration estimate only as an advisory and a watchdog as backstop.

## 4. State machine

Reference logic implements exactly this machine (see
[`roe/drop_off_response.py`](./roe/drop_off_response.py)); table below is the
normative description.

| Phase | Meaning | Enter | Exit to | Action published |
|---|---|---|---|---|
| `CLEAR` | No ledge. Normal nav. | initial, after any resume/reset | `STOPPED` | none |
| `STOPPED` | Ledge asserted. Robot holds position. | ledge assert | `VERIFYING` (re-assert mid-response) / `BACKING_OFF` (persistence met) / `RESUMING` (transient after release-grace) | `stop=True` |
| `VERIFYING` | Persistence re-check after a re-assert during a response | re-assert mid-motion | `BACKING_OFF` / `RESUMING` | `stop=True` |
| `BACKING_OFF` | Reverse straight away from edge. | persistence confirmed | `REORIENTING` (odometry target reached) / `PAUSED_AT_EDGE` (watchdog) | `back_off=True` |
| `REORIENTING` | Turn in place away from the edge. | back-off target reached | `RESUMING` (node-acknowledged) / `PAUSED_AT_EDGE` (watchdog) | `reorient=True` (CCW = away) |
| `RESUMING` | One-shot hand-back to navigation. | any successful exit | `CLEAR` immediately after emitting | `resume=True` |
| `PAUSED_AT_EDGE` | Autonomous escape exhausted or a phase missed its deadline. Robot holds and alerts. | exhaustion / watchdog | `CLEAR` (operator resume or reset) | `stop=True`, `alert=True` (every tick) |

### 4.1 Normal successful escape

```
cliff assert ──> STOPPED ──persistence──> BACKING_OFF ──odometry target──>
REORIENTING ──node confirms heading──> RESUMING (hand back to nav) ──> CLEAR
```

Total motion: one reverse of `back_off_distance_m` (default 0.25 m, estimate)
plus one in-place turn away from the edge (default ≈1.0 s, estimate). After
resume, navigation continues along a heading that no longer overhangs the
edge.

### 4.2 Escape failure escalation (same edge, within a retrigger window)

If the SAME edge re-triggers within `retrigger_window_sec` (default 8 s,
estimate) of a resume, the response escalates: `back_off_escalation_m` and
`reorient_escalation_sec` (larger manoeuvre). After `max_edge_recurrences`
(default 3) recurrences of the same edge, the machine enters `PAUSED_AT_EDGE`:
**pause + alert** (Home Assistant / operator *and* reason code in status). A
trigger *outside* the retrigger window resets the cluster (it is a different
location/problem).

This is intentionally conservative: a vacuum that repeatedly stops on one
edge has either met a genuine dead-end geometry (e.g. a drop at the dock, a
floor-level threshold taller than the bot) or a faulty sensor — both warrant a
human's attention sooner rather than an endless cycle of futile escapes.

## 5. Sensor handling details

### 5.1 Cliff (anti-fall IR, priority 2)

- **Source of truth:** four IR cliff sensors, aggregated by the MCU bridge
  into `/oomwoo/safety/cliff` (`std_msgs/msg/Bool`), matching xbattlax's
  existing subscription. Per-side resolution (`left-up/left-down/right-up/
  right-down` from part-specs) is available via the GD32 sensor packet for a
  future per-side refinement; the Bool aggregate is sufficient for the
  response machine.
- **Level-triggered, not edge-triggered:** because a cliff Bool can be
  asserted persistently, the hosting node MUST poll / handle level, and
  re-feed `on_ledge_asserted` if a persistent edge is still active after the
  manoeuvre (edge-triggered callbacks alone will silently miss it). The
  response machine returns a `stop=True` action on every tick while in
  `STOPPED`/`VERIFYING` so a level-based stop is trivially implemented.

### 5.2 Debounce / transient rejection

A cliff assertion must persist for `persistence_sec` (default 0.25 s,
estimate) before any back-off is commanded; a release inside that window (or
inside the subsequent `release_grace_sec`) is reported as
`TRANSIENT_CLEARED` with **no motion executed**. Rapid blips therefore cost
nothing except a brief hold. Threshold values are estimates to sweep in sim/hw
(§7).

### 5.3 Wheel-drop discrimination (priority 3)

`DropOffResponseController.classify_wheel_drop(commanded_progress_m)`
classifies a wheel-drop as **ledge** (no commanded forward progress over the
recent window) or **transient traction** (progress present — the wheels
temporarily left the floor crossing an uneven threshold/object, but the robot
is still advancing under command). Only the ledge case feeds the response
machine. The discrimination threshold `WHEEL_DROP_PROGRESS_THRESHOLD_M` is an
estimate.

Rationale: full robotic vacuums routinely produce wheel-drop pulses when
rolling off-and-onto furniture lips, area rugs, or cable lumps; treating every
pulse as a ledge would stall the mission constantly. The same caveat that
applies to xbattlax's Bool pause applies here: the *node* must integrate the
odometry window before calling the classifier.

## 6. Integration with the merged recovery node

Minimal, non-breaking integration points (see also
[integration-cmd-vel-hold-and-watchdog.md](./integration-cmd-vel-hold-and-watchdog.md)
for the cmd_vel-hold discipline):

1. **Bypass the empty pause for ledge events.** In `recovery_node.py`, the
   `_cliff_cb` / `_wheel_drop_cb` callbacks currently do
   `trigger(Situation.CLIFF)` which pauses with no ladder. Replace that call
   *for ledge kinds* with the drop-off response flow; keep the pause for
   `E_STOP` and `PICKUP` exactly as-is. (Alternative, lowest-touch: keep the
   xbattlax controller untouched and put the drop-off response in a separate
   node with higher arbitration priority — see item 4.)
2. **Status.** Emit the escape state transitions into the same `/oomwoo/status`
   JSON schema (DESIGN §6): a new `PHASE`-level block with reason codes
   listed in §7.
3. **Hand-back.** `resume=True` must hand /cmd_vel back to Nav2 **only after**
   the watchdog/follower window allows — the same rule as
   operator-override-and-resume.md: never fight another /cmd_vel publisher.
4. **Priority over the merged node (recommended deployment).** Because the
   merged node pauses CLIFF on its own, a clean non-invasive deployment is:
   keep `oomwoo_recovery_safety` as the bumper/recovery controller, and host
   the drop-off response in a **separate safety node** subscribed to the same
   `/oomwoo/safety/*` topics, publishing `cmd_vel` (zero + escape manoeuvres).
   The `DropOffAction` `stop`/`back_off`/`reorient` fields map 1:1 to
   `geometry_msgs/msg/Twist`, and the `alert` field maps to a status/HA event.
   Per DESIGN §5 arbitration rule 1 the safety response takes precedence, so
   both nodes must be wired so cliff-stop wins over bumper recovery (the
   watchdog/follower chain — or a simple priority on the base — decides; this
   must be validated in sim before hardware).

### 6.1 Pause-and-alert surface

On `PAUSED_AT_EDGE`, publish (in addition to `/oomwoo/status`):

- `std_msgs/String` on `/oomwoo/recovery/alert` (new) with reason code
  `LEDGE_PAUSE_EXHAUSTED` or `LEDGE_PHASE_TIMEOUT`; and
- Home Assistant notification template (DESIGN §6 already ships an HA block)
  — alert state `paused_at_edge`, e.g. "Robot is stuck at an edge and needs
  help" plus side/kind metadata. All strings are integration proposals;
  exact telemetry schema is open for review.

## 7. Status reason codes (addition to DESIGN §6)

| Code | State | Meaning | Recoverable |
|---|---|---|---|
| `LEDGE_DETECTED` | stopped | Ledge asserted, robot holding | Yes |
| `LEDGE_TRANSIENT_CLEARED` | resuming | Blip rejected, no motion executed | Yes |
| `LEDGE_BACKOFF` | recovering | Reverse away from edge (odometry-targeted) | Yes |
| `LEDGE_REORIENT` | recovering | Turn away from edge | Yes |
| `LEDGE_ESCAPED` | resuming | Manoeuvre succeeded, nav resumed | Yes |
| `LEDGE_PAUSE_EXHAUSTED` | paused | Same edge recurred too often → alert | Yes (operator/reset) |
| `LEDGE_PHASE_TIMEOUT` | paused | A manoeuvre missed its deadline → alert | Yes (operator/reset) |

Reference-logic fields map to these via `DropOffAction.reason` /
`DropOffOutcome`; the actual serialised shape is for the node to finalise.

### 8.2 Sim (manual injection until sim adds cliff sensors)

1. Launch oomwoo-one world; drive toward a ledge in the model or inject
   `/oomwoo/safety/cliff` Bool `True` via `ros2 topic pub` (and/or
   `/oomwoo/safety/wheel_drop`).
2. Verify: immediate stop (no displacement), then after persistence the
   robot reverses the configured distance and turns away, `/oomwoo/status`
   reports `LEDGE_BACKOFF` → `LEDGE_REORIENT` → `LEDGE_ESCAPED`, nav resumes.
3. Verify transient rejection: publish a `< persistence_sec` pulse → no
   motion commanded, status `LEDGE_TRANSIENT_CLEARED`.
4. Escalation: re-assert within `retrigger_window_sec` 3× → `LEDGE_PAUSE_EXHAUSTED`
   + alert; verify the robot holds still and the HA/alert surface fires.
5. Wheel-drop discrimination: command forward progress while asserting
   wheel-drop → no escape; assert with zero progress → escape triggers.

Suggested follow-up upstream (`oomwoo_gazebo`, by whoever picks it up): add a
cliff sensor (downward IR/range, per OOMWOO part-specs) and a world with a
ledge, so these scenarios automate instead of requiring manual injection. This
matches DESIGN.md open question #3 (wheel-drop/pickup not simulated) — extend
that work to cliff.
